04 / How I Think

How I Think
About Products

Hover any card to see the reasoning behind the principle.

01

A technically impressive solution can still solve the wrong problem.

Implementation isn't the hardest part.

I've repeatedly found that the hardest part isn't implementing the model.
It's deciding what should actually be measured, and ensuring the technical effort aligns with a real user workflow.

02

I don't trust a metric without understanding what changed.

Numbers need context.

A +15% improvement sounds useful, but I'd still want to know what changed in the data, feature set, evaluation method and user workflow.
Metrics are the start of the conversation, not the end.

03

I try to make the trade-off explicit: what are we gaining, and what are we giving up?

Validation over velocity.

If I can test the assumption with a smaller experiment, I'd rather do that before committing engineering effort.
The goal is to learn what works, not just ship what was planned.

04

I don't assume every friction point deserves a feature.

Context matters.

Some friction is intentional. Some is caused by constraints.
Some is actually useful friction (like adding a confirmation step to prevent data loss).
Understanding the *why* prevents building the wrong *what*.

05

If the metric doesn't move, I want to understand why before calling the idea successful.

The PR merge is day zero.

A feature isn't finished when the PR is merged.
The interesting part starts when real users interact with it.
That's when we find out if our hypothesis was actually right.
