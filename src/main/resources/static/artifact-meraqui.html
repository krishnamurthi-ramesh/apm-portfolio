AI Candidate Matching & ERP Integration

A condensed product spec recreating my requirements-to-shipping loop for karam.ai. This covers problem framing, success metrics, model trade-offs, and risk mitigation.

The Problem

Recruiters spend significant time manually parsing candidate profiles and cross-referencing them against JD requirements in our ERP system. The existing keyword-matching system yields high recall but extremely low precision — forcing recruiters to read every profile anyway.

Problem Statement

"Recruiters at Meraqui lack a reliable, context-aware way to instantly identify top-fit candidates for a JD within the ERP workflow, leading to duplicated manual data entry and slow time-to-shortlist."

Target Users & Journey

  • Primary User: Technical Recruiters & Talent Acquisition Specialists.
  • Current Journey: Receive JD → Search ERP via boolean/keywords → Export list → Manually read resumes → Manually update ERP shortlist status.
  • Proposed Journey: Upload JD to ERP → System auto-surfaces top 10 ranked candidates with LLM-generated justification → Recruiter approves/rejects with one click.

Success Metrics

If we build this, how do we know it worked?

Primary (Quality)
Matching Precision@10: Percentage of the top 10 recommended candidates that are actually shortlisted by the recruiter.
Secondary (Effort)
Manual Data Entry Reduction: Measured by the decrease in manual profile updates/status changes in the ERP.
Counter (Risk)
Downstream Inconsistencies: Tracked via schema-validation failure rates in the ETL pipeline.

AI Trade-offs & Decisions

Building the model isn't the challenge. Deciding which model architecture serves the product constraint is.

Approach Latency Cost Accuracy / Context Decision
Zero-shot API (GPT-4) High (2-4s per candidate) High ($$$ per run) Excellent reasoning, but struggles with niche internal skill taxonomies. Discard. Too slow and expensive for bulk ERP screening.
Pure Semantic Search (Embeddings) Very Low (<100ms) Negligible Good recall, poor precision. Misses "years of experience" logic (e.g., 5 vs 2 years). Discard as standalone. Doesn't solve the core problem.
Fine-tuned smaller LLM + Hybrid Retrieval Moderate (~800ms batch) Low (In-house compute) High precision for our specific taxonomy. Captures complex JD requirements. Selected. Optimized for our specific domain at acceptable latency.

Risk Mitigation & Constraints

  • Risk: Hallucinated Skills. LLMs can hallucinate that a candidate possesses a skill simply because it appeared contextually in their resume (e.g., "Company X uses Java" vs "I coded in Java").
    Mitigation: Strict schema validation in the ETL pipeline. If the extracted skill isn't in our verified taxonomy database, it's flagged for human review.
  • Risk: Black-box Rejection. Recruiters won't trust an AI that rejects candidates without explanation.
    Mitigation: The UI must surface a 2-sentence generated justification for why a candidate scored highly, referencing specific lines in their resume.

Outcomes & PM Reflection

What I actually did

  • Partnered with stakeholders to define success metrics (precision, manual entry reduction) before code was written.
  • Drove feature engineering and LLM fine-tuning to improve matching context.
  • Specified ERP integration endpoints, defined API contracts, and built testing suites for the deployment.

Impact: +15% matching precision · −15% manual data entry · −12–15% downstream inconsistencies.

PM Reflection: How I would improve it today

  • Instrumentation: I'd add telemetry to track exactly why a recruiter rejected a highly-ranked candidate (e.g., "Overqualified" vs "Wrong domain") to feed back into the model evaluation.
  • User Research: I'd shadow 3-4 recruiters using the new tool to see if the 2-sentence justification actually builds trust, or if they still open the full resume out of habit.
  • Next Iteration: Move from batch API scoring to streaming responses so recruiters see top candidates populate instantly as the JD is typed.
