Product Teardown

PhonePe — what breaks when lending is a marketplace, not a lender

Same category as KreditBee, a different business model, and a genuinely different friction point — the hand-off, not the documents.

§T1

Funnel, as it actually exists today

  1. Discover
    User opens "Loans" / "Financial Services" inside the PhonePe app — already trusted, already has UPI history there.
  2. Choose offer
    Selects a loan type/amount from pre-approved offers, sourced from PhonePe's lending partners (e.g. DMI Finance and other RBI-registered NBFCs). PhonePe itself doesn't lend — it brokers.
  3. Hand-off
    User is redirected to the partner lender's own application flow, inside or alongside the PhonePe shell.
  4. Re-enter details
    Personal, income, and employment details, plus PAN — sometimes information PhonePe already has.
  5. KYC
    Mostly OTP-based e-KYC, minimal document upload.
  6. Review offer & e-sign
    Loan agreement signed digitally.
  7. Disbursal
    Funds credited — within minutes to a few hours/days depending on partner.
  8. Repayment setup
    Autopay must be set up separately, after disbursal — a second, distinct onboarding task.
§T2

Where the friction actually is

KreditBee is a single-lender product, so its whole flow lives in one system with one voice. PhonePe's lending business is structurally different: it's a marketplace, brokering between the user and multiple partner NBFCs. That structural choice creates a friction type KreditBee doesn't have at all.

Friction point The hand-off. The user starts inside an app they already trust — used daily for UPI — then gets routed into a partner lender's own application flow, in a different visual language, sometimes re-asking for information PhonePe already has. This isn't a documentation problem like KreditBee's; it's a continuity and trust problem. Every hand-off is a moment the user has to re-decide "do I trust this."

A second, smaller friction point: Autopay setup is decoupled from loan approval. A user who's just been approved and is relieved to have funds is handed a second onboarding task rather than one continuous flow — exactly where a relieved, distracted user drops off and quietly creates a collections problem weeks later, not a UX metric today.

§T3

The fix

Proposal 1 — highest leverage Keep the experience inside PhonePe's own native context, even when the underlying lender changes. An in-app AI agent that already has the user's PhonePe-known details (name, PAN if previously used, income if inferred from transaction history with consent) could carry that context across the hand-off — pre-filling and simply confirming rather than asking the user to retype.
Proposal 2 Fold Autopay setup into the same approval flow, framed as the last step of getting the loan — "you're approved; here's your one remaining step before funds move" — instead of a disconnected follow-up.

This is close to exactly what Revrag's embedded, multilingual in-app agents are built to do for BFSI onboarding: absorb the partner-integration complexity so the user only ever experiences one continuous conversation, never a hand-off. I'm noting that directly rather than treating it as a coincidence.

§T4

Metric that would prove it worked

Primary Hand-off completion rate — of users who select a loan offer, what fraction complete the partner application without abandoning at the redirect or the re-entry-of-details step. This is the metric KreditBee's funnel doesn't need but PhonePe's does, precisely because the marketplace model is the source of the friction.
SecondarySame-session Autopay setup rate — of users disbursed a loan, what fraction complete repayment mandate setup in the same session rather than days later, or never, until a missed EMI.

Together with the KreditBee teardown, this shows the same category read two different ways depending on the underlying business model — not one insight copy-pasted onto two logos.
